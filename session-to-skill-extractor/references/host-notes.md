# Host Notes — Detection, Session Sources, Skill Install Locations, Scheduling

Rewrite of spec C3, replaced with the actual verified values gathered 2026-09-17 (Appendix A web research + local inspection while building the adapters in this project). Every fact below carries one of three tags:

- `verified: yes (2026-09-17, local inspection)` — confirmed by reading real files/env on the machine this skill was built on.
- `verified: yes (2026-09-17, <docs URL>)` — confirmed against that host's current official documentation.
- `verified: no — best guess, probe at runtime` — not confirmed either way; the adapter degrades gracefully (never crashes) if the guess is wrong, and the skill should fall back to asking the user rather than trusting it blindly.

The Agent Skills spec itself (frontmatter contract every emitted `SKILL.md` must satisfy): `name` + `description` required; `name` 1–64 chars, lowercase `a-z`/`0-9`/hyphens, no leading/trailing/consecutive hyphens, must match the containing directory name; `description` 1–1024 chars; optional `metadata` (string→string map), `license`, `allowed-tools` (experimental), `compatibility` (≤500 chars). `verified: yes (2026-09-17, https://agentskills.io/specification)`.

## claude-code

- **Detection signals**: env `CLAUDECODE=1`, documented for subprocesses Claude Code spawns (tools/hooks/MCP). `verified: yes (2026-09-17, https://code.claude.com/docs/en/env-vars)`. Presence of `~/.claude/` and a `.claude/` dir in cwd is a supporting filesystem signal. `verified: yes (2026-09-17, local inspection)`. The cascade in `scripts/detect_host.py` treats `CLAUDECODE == "1"` as confidence `high` and short-circuits everything else.
- **Session source**: local transcripts at `~/.claude/projects/<encoded-cwd>/<session-id>.jsonl`, one JSONL file per session, cwd encoded by replacing `/` with `-`. `verified: yes (2026-09-17, https://code.claude.com/docs/en/claude-directory)` for the path and the 30-day default retention (`cleanupPeriodDays`). The field-level JSONL schema (`type: "user"|"assistant"` plus meta types like `file-history-snapshot`/`attachment`/`mode`; `message.content` as either a plain string or blocks of `text`/`thinking`/`tool_use`/`tool_result`) is **not** officially documented — the adapter in `scripts/adapters/claude_code.py` was written and tested directly against real local `.jsonl` files. `verified: yes (2026-09-17, local inspection)` for the schema; the shape may still drift across Claude Code releases since it is not a public contract.
- **Skill install locations**: `.claude/skills/<name>/SKILL.md` (project, discovered walking up nested directories) and `~/.claude/skills/<name>/SKILL.md` (user). `verified: yes (2026-09-17, https://code.claude.com/docs/en/skills)`.
- **Scheduling**: native scheduled tasks, plus cloud-hosted Routines. `verified: yes (2026-09-17, https://code.claude.com/docs/en/scheduled-tasks)`.

## codex

- **Detection signals**: `scripts/detect_host.py` treats any env key with the `CODEX_` prefix as a medium-confidence `codex` signal. `CODEX_HOME` (default `~/.codex`) and sandboxed-child variables `CODEX_SANDBOX` (e.g. `seatbelt`) / `CODEX_SANDBOX_NETWORK_DISABLED=1` are documented. `verified: yes (2026-09-17, https://developers.openai.com/codex/concepts/sandboxing)`. Whether a *bare, non-sandboxed* Codex CLI invocation always exports a `CODEX_*` variable into the agent's own environment (as opposed to only into sandboxed subprocesses) is `verified: no — best guess, probe at runtime`; presence of `~/.codex/` is a supporting filesystem signal.
- **Session source**: local rollout logs at `~/.codex/sessions/<YYYY>/<MM>/<DD>/rollout-<ISO-ts>-<uuid>.jsonl`, one JSON object per line, each line shaped `{"ordinal", "timestamp", "type", "payload"}` (`type` values include `session_meta`, `response_item` with a nested `payload["type"]` of `message`/`function_call`/`custom_tool_call`/`function_call_output`/`custom_tool_call_output`/`reasoning`/`agent_message`, plus telemetry types that are skipped). This schema is **not** officially documented; `scripts/adapters/codex.py` was written and tested directly against real local rollout files. `verified: yes (2026-09-17, local inspection)`.
- **Skill install locations — corrected from the original build spec**: the current official location is `$CWD/.agents/skills` (and parent directories), the user-level `~/.agents/skills`, and `/etc/codex/skills`. `~/.codex/skills` is **legacy** and should not be treated as the primary install target for newly emitted skills. `verified: yes (2026-09-17, https://developers.openai.com/codex/skills)`. Note: this docs domain has exhibited redirects to `learn.chatgpt.com` and some 404s during verification — re-probe before relying on the URL long-term.
- **Scheduling**: Codex app Automations. `verified: yes (2026-09-17, https://developers.openai.com/codex/skills)` (mechanism name only; exact configuration UI not probed).

## devin

- **Detection signals**: no local CLI markers exist for Devin (no `~/.devin/` equivalent confirmed); detection relies on Devin's own system context self-identifying, and `scripts/detect_host.py` treats any `DEVIN_*` env var as a medium-confidence fallback signal. `verified: no — best guess, probe at runtime`.
- **Session source**: Devin has no local transcript store, so the adapter (`scripts/adapters/devin.py`) is **paste/export-first** by design (owner decision, spec E4): it primarily reads a pasted or exported session-detail JSON. Optionally, if `DEVIN_API_KEY` is set in the environment, it falls back to the Devin API: `GET https://api.devin.ai/v1/sessions` (list) and `GET https://api.devin.ai/v1/sessions/{session_id}` (detail, `messages[]` of `{type, event_id, message, timestamp, origin, username}`), authenticated with `Authorization: Bearer $DEVIN_API_KEY`. `verified: yes (2026-09-17, https://docs.devin.ai/api-reference)`. The `v1` API surface is documented as deprecated-but-working; `v3` (`/v3/organizations/*`) is the currently recommended surface — the adapter targets `v1` for now. `verified: yes (2026-09-17, https://docs.devin.ai/api-reference)` for the deprecation notice; migrating the adapter to `v3` is future work, not done in this build.
- **Skill install locations**: Devin's native mechanisms are Knowledge and Playbooks, but this extractor still emits a portable `SKILL.md` into the target repo for consistency with every other host (owner requirement B3/B4); whether Devin also reads repo `SKILL.md` files directly, or only Knowledge/Playbooks, was not confirmed. `verified: no — best guess, probe at runtime`.
- **Scheduling**: Scheduled Sessions / Automations. `verified: no — best guess, probe at runtime` (mechanism name surfaced during research but not independently confirmed against a docs page).

## copilot

- **Detection signals**: `scripts/detect_host.py` treats any env key with the `COPILOT_` prefix as a medium-confidence signal. Copilot CLI documents user-set config env vars `COPILOT_MODEL`, `COPILOT_HOME`, `COPILOT_GITHUB_TOKEN`, but whether the CLI itself *exports* `COPILOT_*` into spawned child-process environments (as opposed to only reading them) is unconfirmed — kept as a medium-confidence signal, not a hard match. `verified: no — best guess, probe at runtime`. Presence of `~/.copilot/` is a supporting filesystem signal. `verified: yes (2026-09-17, local inspection)`.
- **Session source**: current official docs describe `~/.copilot/session-state/<id>/` plus a SQLite `~/.copilot/session-store.db`, with `history-session-state/` called out as the legacy layout. `verified: yes (2026-09-17, https://docs.github.com/en/copilot/concepts/agents/copilot-cli/chronicle)`. On the machine this skill was built and verified on, **neither** `session-state/` nor `history-session-state/` was present; the only thing found under `~/.copilot` was a `data.db` SQLite file whose `sessions` table is **metadata only** (columns like `id`, `title`, `session_type`, `model`, `created_at`, `updated_at` — no message bodies). `verified: yes (2026-09-17, local inspection)`. `scripts/adapters/copilot.py` therefore probes, in order: `session-state/<id>/*.json` (best-effort — the exact per-file name(s) Copilot writes inside each session directory is `verified: no — best guess, probe at runtime`), then `history-session-state/<id>/state.json` (legacy shape `{"sessionId","startTime","chatMessages":[{"role","content"}]}`, itself `verified: no — best guess, probe at runtime`, since it could not be confirmed against a real install), then `session-store.db`, then `data.db`. A DB-only hit produces a single-turn `Session` summarizing the metadata row, with `outcome_signals.notes` pointing at the paste fallback for full message text — the SQLite tables never contain message bodies on this install, so full-content extraction from Copilot requires a pasted transcript.
- **Skill install locations**: repo-level `.github/skills/`, `.claude/skills/`, and `.agents/skills/`; user-level `~/.copilot/skills/` and `~/.agents/skills/`. `verified: yes (2026-09-17, https://docs.github.com/en/copilot/concepts/agents/about-agent-skills)`.
- **Scheduling**: Copilot CLI scheduled prompts, plus cloud-agent Automations. `verified: yes (2026-09-17, https://docs.github.com/en/copilot/concepts/agents/about-agent-skills)` (mechanism name only).

## generic

- **Detection signals**: none of the above match — this is the cascade's fallback (`confidence: "low"`), and it is intentionally non-fatal: the skill never refuses to run, it falls back to asking the user.
- **Session source**: `scripts/adapters/generic.py` reads a user-supplied file path, glob pattern, or pasted text. It auto-detects the shape: JSONL with one `{"role": ..., "text": ...}` object per line, or blank-line-separated `User:`/`Assistant:` blocks, or (as a last resort) the whole input treated as a single user turn.
- **Skill install locations**: ask the user where their skills live; default to `./skills/<name>/SKILL.md` if they have no preference.
- **Scheduling**: whatever generic cron/launchd/task-scheduler mechanism the user's own environment offers; this skill has no host-specific automation to point at for `generic`.
